BDC Footnote Tape

Any BDC 10-K or 10-Q in. One row per loan, with its footnotes resolved, out.

Private creditPublic SEC dataWorking demo

Problem

A BDC prints each loan's status (non-accrual, PIK, restricted) as a footnote marker defined pages away from the row, so a usable loan tape costs an analyst a manual rebuild of every schedule, for every lender, every quarter (hours per filing: unobserved).

For

PlayerPrivate credit fund or allocator that reads BDC filings as public evidence on private loans. A BDC (business development company) is a listed lender that files its loan book with the SEC each quarter.
UserCredit analyst: decides which borrowers to review this quarter, e.g. names another lender has put on non-accrual.
BuyerHead of credit data: decides whether to load this tape, buy a vendor dataset, or keep re-keying.

User stories

  1. As a credit analyst, I want any BDC 10-K or 10-Q turned into one row per loan with its footnote flags, so that I see which borrowers a lender marks non-accrual or PIK without re-keying the schedule.
  2. As a credit analyst, I want each flag shown next to the footnote text and the filing link, so that I can check a status before it goes into a credit memo.
  3. As a head of credit data, I want every filing reconciled to its own total, with unresolved markers listed, so that I load passing files without re-checking each row.

Try it

  1. Pick an example filing, or paste a SEC EDGAR URL, an accession number or a ticker.
  2. Click Run. Seven steps report as they finish: fetch, locate, parse, standardise, footnotes, resolve, QA.
  3. Read the QA table, tick "Only non-accrual candidates", trace one loan to its footnote text, then download the CSV, JSON and data dictionary.

Real filings are fetched live from SEC EDGAR and labelled public SEC data. An offline synthetic sample is included. Rules only: no language model is called. Limits: 25 MiB per filing, 10 filings per visit.

Verdict: likelihood is the weakest factor for both.

  • Analyst fix: hand-label non-accrual rows on 10 filings against each filer's own non-accrual disclosure. This turns "keyword match" into a measured precision.
  • Buyer fix: run the demo pipeline over the 1,805 filings already on disk (download_bdc_filings.py output) and publish the pass rate per filer. No new code: a loop over pipeline.run.
Sub-problems
  1. Find. The schedule sits somewhere in a 6 to 60 MB filing, often in two dated copies. Proof: demo/vendor_parallax/section.py find_sections, demo/soi_parse.py choose_section.
  2. Parse. Each filer prints its table differently: split rows, continuation pages, units in thousands or millions. Proof: demo/vendor_parallax/tables.py find_header, classify_rows; demo/soi_parse.py. Partial: a layout with no company column parses 0 rows.
  3. Resolve. Status lives in footnote markers defined pages away from the row. Proof: demo/footnotes.py calling the repo's parsers/footnote_extractor.py; marker lookup in demo/pipeline.py step 6.
  4. Trust. A missed table looks like a clean file unless something checks it. Proof: demo/pipeline.py step 7, totals vs the filing's own total row, unresolved markers.
  5. Confirm. A footnote that mentions non-accrual is not always a loan on non-accrual. The repo has a Gemini confirmer (qa_reviewer/non_accrual_confirmer.py); the demo leaves it off.
  6. Match names. The same borrower has different names at different lenders.
  7. Track change. A status matters most when it changes between quarters. The demo reads one filing at a time.

This build tackles 1 to 4.

How it works
  1. Fetch: URL, accession, ticker or upload -> filing bytes. SEC User-Agent, 5 requests per second, disk cache, 25 MiB cap.
  2. Locate: filing -> dated schedule sections. The EDGAR period is picked, else the latest date.
  3. Parse: every table in the section -> rows, with headers mapped by token. Headerless continuation pages inherit the mapping.
  4. Standardise: rows -> one row per position: issuer, industry, instrument and lien bucket, reference rate, spread, maturity, par, cost, fair value, markers. Money scaled to dollars.
  5. Footnotes: section -> {marker: text}, with the repo's own extractor. Three demo guards: clip at the next dated section, strip the filer's page header, cut text that runs into the notes.
  6. Resolve: each row's markers -> footnote text and tags (non-accrual, PIK, restricted, non-qualifying, affiliate, Level 3, unfunded, non-income producing, pledged).
  7. QA: fair value and cost vs the filing's own total (pass within 1%), unresolved markers, rows missing values, rate cells that didn't parse.
  8. Export: positions CSV, footnotes CSV, JSON, data dictionary (37 columns).
Hypotheses, one per tackled sub-problem

1 · FIND

Before -> after
analyst scrolls to the schedule and checks its date -> section located and dated, EDGAR period picked
Hypothesis
If the schedule is located and dated from the filing itself, then the analyst reaches the first loan row sooner, because no one searches a 6 to 60 MB document by hand.
Metric
Share of filings where the parsed date equals the EDGAR period. Up. Observed 4 of 4. Analyst baseline unobserved. Guardrail: rows or footnotes taken from the prior-period section stay at 0.
Test
50 filings drawn at random from the 1,805 on disk. Count date matches and prior-period leaks.

2 · PARSE

Before -> after
rows re-keyed into a spreadsheet -> one row per position, scaled to dollars
Hypothesis
If headers are mapped by token and units read from the page, then most filings yield a full tape with no hand edits, because layout differences become rules instead of re-keying.
Metric
Share of filings whose parsed fair value is within 1% of the filed total. Up. Observed 4 of 4 tested; 1 extra filing parsed 0 rows. Corpus baseline unobserved.
Test
Same 50-filing sample, grouped by filer.

3 · RESOLVE

Before -> after
flip to the footnote pages, match markers by eye -> each row carries its footnote text and tags
Hypothesis
If each marker is replaced by its definition on the row, then the analyst finds non-accrual and PIK loans without opening the filing, because the status is a column, not a cross-reference.
Metric
Distinct markers resolved. Up. Observed 76 of 76 across 4 filings. Non-accrual flag precision unmeasured.
Test
Hand-label non-accrual rows on 10 filings; compare with the flag.

4 · TRUST

Before -> after
no check on the extraction -> QA per filing: totals, unresolved markers, empty parse
Hypothesis
If every filing shows whether it reconciles and which markers failed, then the head of data loads passing files without re-checking rows, because failures are visible before load.
Metric
Share of loaded filings later corrected by hand. Down. Baseline unobserved.
Test
Planted defects: the synthetic sample has 2, and QA catches both (tests). Next: plant 10 defects in real filings and count catches.

  • Hypotheses 1 and 2: 4 of 4 filings parsed the EDGAR period and reconciled. A fifth, a Blackstone Private Credit Fund 10-K on disk (32.5 MB), parsed 0 positions: its table has no company column. QA shows it as a failed check.
  • Hypothesis 3: 76 of 76 distinct markers resolved. Of Golub's 45 candidate rows, 8 come from an affiliate-table note that only mentions non-accrual, so the flag over-counts there.
  • Guardrail, prior-period leak: before the section clip, Golub's non-accrual footnote read "as of September 30, 2025" inside the June 30, 2026 schedule. After the clip it reads June 30, 2026.
  • Negative amounts read as markers: before the fix, Main Street had 11 and Golub 24 unresolved markers, all negative cost or fair value cells such as "(71)". After: 0.
  • Speed: footnote extraction took 69% to 72% of each run.
  • Memory: peak 667 MB on a 24.5 MB filing, 804 MB on a 32.5 MB filing. This set the 25 MiB cap (Community Cloud guarantees about 690 MB).
  • Filing sizes: 1,805 primary documents on disk: median 6.1 MB, 95th percentile 21.1 MB, max 60.3 MB. 97.5% are at or under 25 MiB.
  • Tests: demo/test_demo.py: 11 passed, 1 skipped offline; 12 passed with the live SEC test on. The Streamlit AppTest run shows no exception.
  • Repo pipeline, earlier run: 4,224 schedule sections from 1,811 filings of 60 BDCs; 102 sections not found; 325 with no footnotes; median 17 footnotes. Source: output/bdc_footnotes_full_pipeline.csv (local, not in git).
  • README claims corrected: "~95% of cases correctly" and "100x faster" have no measurement behind them. The Gemini completeness check in output/logs/qa_run_v15.log passed 25 times and failed 50 times.
Limits and trade-offs
  • Users: no analyst or data lead has used it. Every "before" is assumed.
  • Accuracy: row-level accuracy against hand labels is unmeasured. Reconciliation proves the totals, not each row.
  • Coverage: 4 filers tested plus 1 failure. The pass rate across all BDCs is unobserved.
  • Tags: keyword matches on footnote text. Hypothesis 3's value depends on their precision.
  • Hosting: not yet deployed. Memory figures are from a Mac, not the Cloud container.
