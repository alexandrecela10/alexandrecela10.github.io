BDC Footnote Tape

Give it any BDC's 10-K or 10-Q (annual or quarterly report). Get back one spreadsheet row per loan, with each footnote's meaning attached.

Private lendingPublic SEC dataWorking demo

Problem

A BDC (a stock-listed fund that lends to private companies) must list every loan it holds in each report to the SEC (the US market regulator). Each loan's status, such as "this borrower stopped paying interest", is a small footnote mark next to the loan. The meaning of that mark is printed pages away. To get a usable spreadsheet, an analyst rebuilds the whole list by hand, for every lender, every quarter (hours per report: unobserved). Example: Ares Capital's 10-K lists 1,409 holdings, and their 12 different footnote marks are explained in a separate part of the report.

For

PlayerA private lending fund, or an investor choosing which funds to back, that reads BDC reports as public evidence about private loans. BDC stands for business development company. Each one files its full loan list with the SEC every quarter.
UserCredit analyst, the person at a fund who reviews borrowers. Decides which borrowers to look at this quarter, for example ones another lender has put on non-accrual.
BuyerHead of credit data, the person who runs the fund's loan data. Decides whether to load this spreadsheet, buy one from a data vendor, or keep paying people to retype it.

Terms on this page

  • BDC: a stock-listed fund that lends money to private companies.
  • 10-K and 10-Q: the annual and quarterly reports a BDC files with the SEC.
  • Schedule of investments, or loan list: the table in each report that lists every loan the fund holds.
  • Footnote mark: a small letter or symbol next to a loan, explained pages away.
  • Non-accrual: the borrower stopped paying interest, so the lender stops counting it as income.
  • PIK (payment in kind): interest added to the amount owed instead of paid in cash.
  • Fair value: what the lender says a loan is worth today.
  • Reconcile, or add up: the rows we extract sum to the total the report itself prints.

User stories

  1. As a credit analyst, I want any BDC 10-K or 10-Q turned into one row per loan with its footnote flags, so that I see which borrowers a lender marks non-accrual or PIK without retyping the list.
  2. As a credit analyst, I want each flag shown next to its footnote text and a link to the report, so that I can check a status before I put it in a written review.
  3. As a head of credit data, I want every report checked against its own printed total, with unexplained marks listed, so that I load the files that pass without rechecking each row.

Try it

  1. Pick an example report, or paste a link from SEC EDGAR (the SEC's public filings website), a filing ID (accession number) or a stock ticker.
  2. Click Run. Seven steps report as they finish: fetch, locate, parse, standardise, footnotes, resolve, QA (quality checks).
  3. Read the QA table. Tick "Only non-accrual candidates". Trace one loan to its footnote text. Then download the CSV, JSON and data dictionary (a file describing each column).

Real reports are downloaded live from SEC EDGAR and labelled public SEC data. A made-up offline sample is included. It runs on fixed rules: no language model is called. Limits: 25 MiB per filing, 10 filings per visit.

Verdict: likelihood is the weakest factor for both.

  • Analyst fix: label non-accrual rows by hand on 10 reports, against each BDC's own list of non-accrual loans. This turns "keyword match" into a measured accuracy.
  • Buyer fix: run the demo over the 1,805 reports already downloaded (download_bdc_filings.py output) and publish the pass rate per BDC. No new code: a loop over pipeline.run.
Sub-problems
  1. Find. The loan list sits somewhere in a 6 to 60 MB report, often as two copies with different dates. Proof: demo/vendor_parallax/section.py find_sections, demo/soi_parse.py choose_section.
  2. Parse. Each BDC prints its table differently: rows split over lines, tables continued across pages, amounts in thousands or millions. Proof: demo/vendor_parallax/tables.py find_header, classify_rows; demo/soi_parse.py. Partial: a layout with no company-name column produces 0 rows.
  3. Resolve. Each loan's status is a footnote mark explained pages away from the loan. Proof: demo/footnotes.py calling the repo's parsers/footnote_extractor.py; mark lookup in demo/pipeline.py step 6.
  4. Trust. A missed table looks like a clean file unless something checks it. Proof: demo/pipeline.py step 7, which compares totals with the report's own total row and lists unexplained marks.
  5. Confirm. A footnote that mentions non-accrual doesn't always mean the loan is on non-accrual. The repo has a checker built on Google's Gemini AI model (qa_reviewer/non_accrual_confirmer.py). The demo leaves it off.
  6. Match names. The same borrower goes by different names at different lenders.
  7. Track change. A status matters most when it changes from one quarter to the next. The demo reads one report at a time.

This build tackles 1 to 4.

How it works
  1. Fetch: turns a link, filing ID, ticker or uploaded file into the report itself. Follows the SEC's download rules (identify the caller, 5 requests per second). Saves copies to disk. 25 MiB cap.
  2. Locate: finds the dated loan-list sections in the report. Picks the period EDGAR records for the filing, else the latest date.
  3. Parse: reads every table in the section into rows, matching column headers by keyword. Continuation pages with no header reuse the same column matching.
  4. Standardise: makes one row per holding. Columns: borrower, industry, loan type and lien (who gets repaid first), reference rate, spread, maturity (repayment date), par (amount owed), cost (amount the fund paid), fair value, footnote marks. Amounts are converted to dollars.
  5. Footnotes: builds a list of each mark and its text, using the repo's own extractor. Three demo safeguards: stop at the next dated section, remove the BDC's page header, cut text that runs into the report's notes.
  6. Resolve: gives each row's marks their footnote text and a tag. Tags: non-accrual, PIK, restricted (resale limited), non-qualifying, affiliate, Level 3, unfunded, non-income producing, pledged.
  7. QA: compares total fair value and cost with the report's own total (passes within 1%). Lists unexplained marks, rows missing values and interest rate cells that couldn't be read.
  8. Export: holdings CSV, footnotes CSV, JSON, data dictionary (37 columns).
Hypotheses, one per tackled sub-problem

1 · FIND

Before and after
Before: the analyst scrolls to the loan list and checks its date. After: the section is found and dated, matching the period EDGAR records.
Hypothesis
If the loan list is found and dated from the report itself, then the analyst reaches the first loan sooner, because no one searches a 6 to 60 MB document by hand.
Metric
Share of reports where the extracted date equals the EDGAR period. Up. Observed 4 of 4. Analyst baseline unobserved. Guardrail: rows or footnotes taken from the previous period's section stay at 0.
Test
50 reports picked at random from the 1,805 on disk. Count date matches and previous-period leaks.

2 · PARSE

Before and after
Before: rows retyped into a spreadsheet. After: one row per holding, amounts in dollars.
Hypothesis
If column headers are matched by keyword and units read from the page, then most reports give a full spreadsheet with no hand edits, because layout differences become rules instead of retyping.
Metric
Share of reports whose extracted fair value is within 1% of the printed total. Up. Observed 4 of 4 tested; 1 extra report produced 0 rows. Baseline across all reports unobserved.
Test
Same 50-report sample, grouped by BDC.

3 · RESOLVE

Before and after
Before: flip to the footnote pages and match marks by eye. After: each row carries its footnote text and tags.
Hypothesis
If each mark is replaced by its meaning on the row, then the analyst finds non-accrual and PIK loans without opening the report, because the status is a column, not a cross-reference.
Metric
Distinct marks explained. Up. Observed 76 of 76 across 4 reports. Accuracy of the non-accrual flag unmeasured.
Test
Label non-accrual rows by hand on 10 reports; compare with the flag.

4 · TRUST

Before and after
Before: no one checks the extraction. After: quality checks per report: totals, unexplained marks, empty results.
Hypothesis
If every report shows whether it adds up and which marks failed, then the head of data loads passing files without rechecking rows, because failures are visible before loading.
Metric
Share of loaded reports later corrected by hand. Down. Baseline unobserved.
Test
Planted errors: the made-up sample has 2, and the checks catch both (tests). Next: plant 10 errors in real reports and count catches.

  • Hypotheses 1 and 2: 4 of 4 reports picked the EDGAR period and added up. A fifth, a Blackstone Private Credit Fund 10-K on disk (32.5 MB), produced 0 holdings: its table has no company-name column. The checks show it as failed.
  • Hypothesis 3: 76 of 76 distinct marks explained. Of Golub's 45 flagged rows, 8 come from a note on companies the fund partly owns that only mentions non-accrual. So the flag over-counts there.
  • Guardrail, previous-period leak: before the section cut-off, Golub's non-accrual footnote read "as of September 30, 2025" inside the June 30, 2026 loan list. After the cut-off it reads June 30, 2026.
  • Negative amounts read as marks: before the fix, Main Street had 11 and Golub 24 unexplained marks. All were negative cost or fair value cells such as "(71)". After: 0.
  • Speed: footnote extraction took 69% to 72% of each run.
  • Memory: peak 667 MB on a 24.5 MB report, 804 MB on a 32.5 MB report. This set the 25 MiB cap (the free Community Cloud host guarantees about 690 MB).
  • Report sizes: 1,805 main documents on disk: median 6.1 MB, 95th percentile 21.1 MB, max 60.3 MB. 97.5% are at or under 25 MiB.
  • Tests: demo/test_demo.py: 11 passed, 1 skipped offline; 12 passed with the live SEC test on. The Streamlit AppTest run shows no error.
  • Repo pipeline, earlier run: 4,224 loan-list sections from 1,811 reports of 60 BDCs; 102 sections not found; 325 with no footnotes; median 17 footnotes. Source: output/bdc_footnotes_full_pipeline.csv (local, not in git).
  • README claims corrected: "~95% of cases correctly" and "100x faster" have no measurement behind them. The Gemini completeness check in output/logs/qa_run_v15.log passed 25 times and failed 50 times.
Limits and trade-offs
  • Users: no analyst or data lead has used it. Every "before" is assumed.
  • Accuracy: row-by-row accuracy against hand labels is unmeasured. Matching the printed total proves the totals, not each row.
  • Coverage: 4 BDCs tested plus 1 failure. The pass rate across all BDCs is unobserved.
  • Tags: keyword matches on footnote text. Hypothesis 3's value depends on how often they're right.
  • Hosting: not yet deployed. Memory figures are from a Mac, not the Cloud server.
